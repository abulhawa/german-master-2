# ADR 025: Subject partitions and captured identity generations

Accepted for local v2 account-isolation groundwork, 5 October 2026. Extends ADR 024. This supplies mechanisms used by the current isolated learners; it does not establish production authentication or sign-in/sign-out UX.

Each binding captures a canonical UUID subject and a nonnegative identity generation from the host's identity provider. Before a request and after its response/body, the transport checks that the current identity still matches both values. Expiry/sign-out supplies no current identity; a new sign-in generation invalidates old transports even when the subject is unchanged. A stale result cannot clear its frozen pending request. Local drafts and offline work remain readable in their original subject partition. No bearer token is placed in a cache, outbox, namespace or binding.

Web partitions journey/preferences/reports, the IndexedDB reserve/started sessions and the tab-ownership lock by subject. Account or generation replacement remounts the owned learner tree so the prior learner's screen/draft cannot appear in the new account. Owned non-primary database connections close after their outstanding lease operations settle. Native uses UUID-derived app-private AtomicFile names, persists the subject in the cache and refuses a cache belonging to another subject. Its API decorator guards every read and write, and replacing the repository resets the Compose learner tree, even while the new refresh is pending.

The established primary public fixture retains its existing namespaces/files and claims only that known fixture's unbound records. Empty new partitions may be bound to any explicit subject. This is preservation of disposable development work, not a historical migration requirement for v2 production. Runtime defaults bind the known primary fixture subject; they do not invent a second authentication mechanism, discover legacy credentials, or silently attach guest data to an account.

Account-bound transports send the optional v2 `X-Learner-Subject` header. The API compares it with the subject supplied by its verified host authentication callback, before reading the body or calling the store. Malformed/mismatched headers return nonretryable HTTP 409 `account_changed`; the header never authenticates the caller. Existing isolated stateless test transports may omit it. A future verified-auth adapter must preserve the captured binding/credential relationship and use these guarded transports; production provisioning and auth lifecycle remain open.

Local verification covers two web subject stores/locks, namespace preservation, expiry, account switching, a stale credential/server-subject mismatch, streamed stale responses, generation renewal and frozen replay. Real HTTP/PGlite checks that only the original subject receives its preferences/evidence. Web component replacement recovers the first learner's draft without creating another session. Native AtomicFile/decorated-repository tests preserve an assisted draft/profile/report through expiry, a stale accepted response, replacement and renewal, while refusing a foreign cache. Native actual authoritative HTTP checks captured-subject rejection; Compose checks that prior pending UI disappears immediately while the next account's refresh remains pending. These are simulated identity/JVM/component checks, not a real auth provider or physical device acceptance.

No database migrations or production resources are created. The next required work is versioned owned privacy/export/deletion and sign-out choices, with verified auth integration only in the designated isolated environment. Account deletion must prevent abandoned uploads; explicit local removal must target only the selected subject and must never silently drop pending work. Consolidate development migrations before establishing the first real staging or production database.

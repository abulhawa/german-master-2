# ADR 029: Configured learner providers and published runtime catalogs

Accepted for isolated implementation, 5 October 2026. No credential retrieval, schema application, content publication, deployment or release is authorized by this decision.

Configured preview hosts use dedicated Supabase providers rather than legacy auth or fixture bearers. Web uses pinned Supabase JS 2.107.0, project-specific storage and PKCE configuration. Native uses the existing pinned Kotlin SDK with an app-private AtomicFile encrypted using AES-GCM and an Android Keystore key, outside backups. Session material never enters learner caches, frozen requests or identity bindings. Missing decryption keys fail without replacement or deletion of the encrypted record. Device encryption acceptance remains open.

Online user verification must match the UUID subject, intended project issuer, authenticated audience/role, session UUID and unexpired credential. Native also checks the provider session after online verification. Captured generation/subject guards surround HTTP exchanges and body consumption. Each request obtains a credential; retries retain their original learner payload. HTTPS, system certificate verification, redirect refusal and subject preconditions apply. Server signature/current-auth-session checks remain authoritative; client JWT parsing is only a precondition.

Web auth events remove the prior learner tree before asynchronous binding; native session-state replacement keys the shell/repository. A fresh same-subject web sign-in can resume completed local sign-out; native offers explicit continuation after verified binding. Sync or local removal precedes current-device provider revocation. Failures leave durable blocked sign-out state; explicit retry retains the original removal choice. Real service/host identity deletion remains disabled and hidden until reauthentication, retention and recovery are integrated.

The isolated entry points accept complete public configuration. Web uses `VITE_V2_AUTH_PROJECT`, `VITE_V2_AUTH_PUBLISHABLE_KEY`, `VITE_V2_API_ORIGIN`. Android `learnerPreview` uses `GM_V2_AUTH_PROJECT`, `GM_V2_AUTH_PUBLISHABLE_KEY`, `GM_V2_API_ORIGIN`, restricted to the approved staging project. Missing all configuration keeps the explicit fixture; partial/invalid configuration fails closed. Only synthetic public-key strings were used for local build/layout checks. Deployed routing, Android release routing, identity and signing remain unchanged.

The API optionally accepts one configured HTTPS web origin. Bounded preflights expose only Authorization, Content-Type and the subject precondition; actual requests still authenticate. Foreign origins, arbitrary headers/internal routes and deletion preflights are refused. Native needs no CORS; same-origin reverse proxy hosting also remains possible.

Network catalog/session creation cannot fall back to foundation IDs. Configuration binds a release UUID, manifest hash and localized target metadata. The database release/targets must be published, revisions approved and every member have evidence identity. Hash validation covers metadata, topic/target definition, payload/rubric, provenance/normalization and variant/context/transfer identity. Missing, stale, unpublished or mismatched configuration fails before session/pack allocation. Fresh snapshots include selected targets and prior owned state, excluding unrelated unpublished targets. Existing sessions/packs replay their pinned release after selection changes or retirement. Generated catalog contracts distinguish `published` from `unpublished_local_draft` on both clients. No database migration was necessary; the clean v2 baseline remains the first-environment schema.

Approved/published SQL fixtures in tests are synthetic records, not independent German review. Actual foundation/30-target drafts remain unpublished; this change installs no catalog and implements no external publisher.

Evidence comprises provider/gateway mocks, mounted web auth-host tests with a stub learner child, actual PGlite catalog/role and local HTTP tests, native JVM/repository checks, builds/lint and local sign-in-screen browser inspection. No live sign-in/revocation, independent PostgreSQL connection, device encryption or physical accessibility result is claimed. Configured hosts currently require online verification before mounting: offline/expired-auth cold launch needs a deliberate last-verified-account view and reauthentication flow. Release routing also remains open. No full M0–M6 gate closes.

Methods were checked against [JS getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [JS signOut](https://supabase.com/docs/reference/javascript/auth-signout), [Kotlin retrieveUser](https://supabase.com/docs/reference/kotlin/auth-getuser) and [Kotlin signOut](https://supabase.com/docs/reference/kotlin/auth-signout).

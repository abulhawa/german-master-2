# ADR 024: Whole-client fixture reconciliation

Accepted for the isolated v2 learners, 5 October 2026. Extends ADR 022 without introducing production authentication or a client mastery policy.

Both learners offer an explicit **Sync all saved work** action. A pass sends only already frozen requests: pending preferences; online session creation, answer/Skip and completion; started offline sessions in durable start order with their events in question order and completion last; pending revision report; pending reserve download. Preferences precede new session allocation. Existing pinned sessions and events do not become adaptive after preference changes. Independent write kinds use this dependency order rather than unreliable client wall-clock ordering.

Each response is validated and committed before the next write. Profile replay reads the current profile before clearing its request. Online answer feedback remains on the current question; reconciliation does not press Continue, create an answer, or invent a session end. Offline receipts remain separate from provisional feedback. A response loss, failed receipt save, network/auth/rate-limit failure, mismatched response or rejected event stops the entire pass. Successful preceding commits remain saved. Explicit retry skips acknowledged work and reuses the exact remaining IDs and payloads. No background retry or error-triggered upload loop is added.

Android holds its repository mutex through the complete pass and reuses the existing atomic write helpers. Archived offline sessions precede the active offline session. Web holds the existing tab ownership lease, now with a FIFO operation queue covering the operation and receipt save. Reports hold ownership through their receipt save, rather than only HTTP. Offline drafts enter that queue before their mutation starts. New web offline starts receive a monotonic ordinal in the same transaction as slot consumption. Older fixture rows retain their bytes and have deterministic ordinal-zero/ID ordering; there are no v2 production users requiring historical migration compatibility.

The Home and active offline sync controls use the coordinated pass. Existing individual online/profile/report actions remain explicit, serialized operations with their original frozen retry behavior; this is not a universal background uploader or a single chronological ledger across unrelated write kinds. An externally refreshed offline desk rereads receipts while keeping its current session, prompt, draft and provisional feedback open. Confirmed Progress is still replaced only by authoritative reads.

This closes fixture whole-client reconciliation groundwork. Production subject partitions, account lifecycle, guest attachment, real expired authentication/account switching, device acceptance, privacy/export/deletion/sign-out and release recovery remain separate M5 requirements. Do not reinterpret the public shared fixture account as verified identity. No database migration is introduced. Consolidate the development chain before establishing the first real staging or production database.

Verification uses local HTTP/PGlite and JVM/Robolectric: a mixed web profile/online answer/offline Skip/end/report/download pass stops after profile receipt failure and accepted-answer response loss; restart delivers the same answer once and then the remaining dependent work. Native authoritative HTTP drains a pending profile, two archived sessions, report and download after accepted-response and receipt-save failures. Native online answer receipt failure blocks the later report. FIFO ownership and durable reserve ordering have client tests. These are engineering checks, not physical-device or independent accessibility acceptance.

# ADR 027: Durable learner privacy controls and isolated v2 staging preparation

Accepted for local implementation and staging preparation, 5 October 2026. External creation and deployment are not authorized by this ADR.

Both fixture clients persist the subject-bound deletion UUID and literal confirmation before delivery. Normal reads, writes and local practice stop behind the durable marker. Web ownership queues and the native repository mutex finish preceding operations before freezing deletion. Lost responses or receipt saves retain the original request and work; an explicit retry replays it. A validated subject/request receipt commits before any local removal. Cleanup failure resumes from that receipt. Completed deletion retains only a terminal local marker and cannot resume the deleted fixture identity. Web clears only its subject's three learner keys and IndexedDB tables; Android replaces only its subject's AtomicFile. Other subjects, unrelated browser caches and the original release application remain untouched. These controls delete local service learning data, not a Supabase identity.

Local sign-out offers sync first or explicitly confirmed local removal. Sync failure preserves access and remaining work. Successful sync retains unsubmitted drafts in the same subject partition. Removal freezes a durable intent before clearing local data, requires no uploads and does not delete server records. A restart remains signed out until explicit same-subject fixture resume; captured identity checks still apply. This is fixture access control, not credential revocation or production authentication. Real reauthentication, Supabase session revocation and identity deletion remain required integration work.

The owner selected a **new** dedicated Supabase project `german-master-v2-staging`, in **ali's Org**, Frankfurt **eu-central-1**. The existing legacy project must never be reused or modified. Read-only creation cost inspection returned 0 per month. Project creation, credential provisioning, schema application, deployment and production changes retain separate approvals.

`db/baseline/v2.sql` is the clean, empty baseline for the first real v2 database. It incorporates current product columns, constraints, indexes and immutable triggers without historical upgrade/backfill SQL, fixture catalog rows or learner data. Its single baseline version replaces the development migration ledger. Transport expiry requires explicit deadlines. The private `gm` schema revokes public table/sequence/function access and enables RLS without policies, so accidental client grants fail closed. Backend roles/policies and network independent-connection verification must be deliberately added before staging runtime access; this is not production least-privilege acceptance.

Development migrations 001–010 remain only for useful disposable/saved fixture verification. The adapter recognizes baseline 1 without running those upgrades or seeding draft content. No historical 2.0 migration compatibility requirement is introduced. No schema or auth change was applied to a Supabase project.

# ADR 028: Network database and verified server authentication

Accepted for isolated implementation, 5 October 2026. No external schema, credentials or deployment operation is authorized here.

The learning engine uses a minimal parameterized SQL/transaction interface. PGlite remains the disposable fixture adapter. The network adapter uses pinned node-postgres, one acquired connection per transaction, transaction-local verified subject context, certificate-verified TLS and safe integer sequence decoding. It never retries an ambiguous commit. Network startup requires baseline 1 and cannot seed fixtures or replay development upgrades.

`db/baseline/backend-access.sql` prepares a non-login, non-owner, non-BYPASSRLS learning role. Owned rows require the verified transaction subject in both USING and WITH CHECK. The role can read shared content, cannot publish/change it, cannot create schema objects, cannot update immutable receipt/evidence rows or remove deletion tombstones. Publishing remains separate. Client roles receive no grants. Authentication derives the scope before constructing a request's store; the subject header remains only a precondition.

Server auth uses pinned Supabase `getUser(token)` online verification. Tokens must match the selected project's issuer, authenticated audience/role, UUID subject/session and unexpired lifetime. Online verified user identity must match and cannot be anonymous. A current owned auth session is mandatory, including its maximum lifetime; expiry is rechecked after verification. User-editable metadata never authorizes access. The auth verifier uses a separate connection/role with column-only SELECT on auth session id/user_id/not_after, not refresh-token material, learning permissions or auth mutations. Connection URL, keys and tokens stay outside source/logs. Auth outages fail closed. No local fixture token is accepted by this verifier.

The network composition exports a server factory and builds separately from the local launcher; it does not load credentials, start listeners or deploy. Real DELETE remains disabled because service learner deletion is not host-auth identity deletion and retention/revocation/reauthentication integration remains open.

Evidence is deliberately bounded: existing full backend suites passed after the interface/server change; PGlite verifies scoped role ownership, pack/Skip/partial completion/export/deletion and foreign/shared preservation. Adapter mocks verify single-connection/context/commit handling and TLS guards; isolated auth fixtures verify session column privileges/lifetime/revocation; mocked online verification checks project/identity/expiry. These do not prove independent network contention, actual Supabase schema compatibility, live auth lifecycle or client sign-in. Both learners remain fixtures. Existing catalog selection/metadata still uses the five-target foundation release; reviewed-catalog runtime routing must be completed before staging learner practice.

References checked: [node-postgres transactions](https://node-postgres.com/features/transactions), [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres), [online user verification](https://supabase.com/docs/reference/javascript/auth-getuser), [session lifecycle](https://supabase.com/docs/guides/auth/sessions). The markdown changelog index could not be retrieved by the browser tool; the current [breaking-change index](https://supabase.com/changelog?types=breaking-change) was checked instead. No relevant connection/getUser breaking change was identified; Node 22 meets the client runtime requirement.

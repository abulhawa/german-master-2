# ADR 030: Saved-account cold launch and explicit v2 build artifacts

Accepted for local implementation, 5 October 2026. This does not authorize credentials, schema installation, deployment, content publication, signing changes or store release.

Local practice and network authentication have separate lifetimes. After successful online verification, the host durably records only the subject UUID in its dedicated project namespace. Browser localStorage and native no-backup AtomicFile retain this reference, never a token. Cold launch may bind only that previously verified subject to its existing owned cache. This is permission to use local saved work, not proof of a current server identity. Missing or damaged references cannot select an arbitrary account. Generations still fence account replacement and stale local writes.

Local bindings refuse network delivery before provider reads. Online bindings verify credentials for every delivery; expired credentials and failed verification do not delete saved work. HTTP 401 pauses network access and retains the local account. Provider events remove obsolete trees; explicit sign-in/account verification creates a new binding. Reauthentication does not automatically deliver frozen requests. Explicit current-device revocation clears the saved-account reference after success. Pending sign-out/removal/revocation and deletion markers remain authoritative across restart; a local binding cannot resume completed sign-out. Native revocation and resume verification also match the captured subject.

The web v2 artifact has a separate root entry and `build:learner-product` command, alongside the existing fixture preview and legacy build. Missing/partial/foreign project configuration fails closed. Only the separately selected staging project, a publishable key and an HTTPS API origin can enable it. Its root service worker caches app assets only, uses a dedicated cache namespace, refuses API navigation fallback, and does not automatically activate updates or clean other caches. Building this artifact does not select it for deployment or establish production recovery acceptance. Current deployment routing stays intact.

Android learner components and credential-aware HTTP move into main sources. Loopback fixture transport and preview activities stay outside release sources. `GM_V2_RELEASE=1` plus complete dedicated staging public configuration selects the v2 MainActivity path in a release build. It preserves application ID, version code and signing configuration. Learner caches for this path use no-backup storage. No release APK/AAB was signed or published. Existing legacy jobs are handled by a factory that completes them without constructing legacy auth/data dependencies; new legacy sync scheduling and direct legacy provider construction are blocked in v2 builds. The preview already uses a plain Application and no legacy worker startup; the new guard protects the opt-in release path and persisted legacy jobs.

The current implementations retain AtomicFile and IndexedDB rather than introduce client scheduling or schema replicas. No migration changes are needed. The clean v2 baseline remains the only intended first-environment schema; development migrations remain fixture-only.

Evidence: provider mocks, mounted web expired-auth/owned-pack restart and explicit sign-in with actual PGlite-generated packs, native repository cold restart with AtomicFile and actual locally generated packs, full offline suites, debug/preview checks, synthetic configured release compilation/lint and a local browser sign-in-layout check. This is not live provider, physical device, configured browser airplane-mode, two-device or independent German review acceptance. No complete milestone closes.

Current SDK behavior was checked against [JS getSession](https://supabase.com/docs/reference/javascript/auth-getsession) and the [breaking-change index](https://supabase.com/changelog?types=breaking-change). Cached sessions remain untrusted for network authorization. The markdown changelog index and Kotlin session-status page could not be consumed; the pinned Kotlin bridge was compiled instead of claiming documentation or live lifecycle verification.

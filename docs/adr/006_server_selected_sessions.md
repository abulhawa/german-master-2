# ADR 006 Server-selected local sessions

Status: Accepted for the isolated demonstration, 4 October 2026.

`mixed-selection-v1` replaces fixture-order allocation in the local API. Selection reads owned persisted target states and UTC review deadlines in the same learner-locked transaction that stores session issuance and questions. It computes eligibility with the injected clock; cached `isDue` never controls selection. Deadlines at or before issuance are eligible. Selection does not write projections or sync changes.

Allocate approximately 8/5/2 at fifteen questions to eligible Needs practice, other due targets, and New targets. Round the due/new reservations down for small sessions and give the remainder to weaknesses. Reallocate missing pools in weak/due/new order. Rank within pools by overdue urgency capped at thirty days, oldest informative evidence, stable target ID, exercise ID and revision. Open with a non-weak target and insert one after three consecutive weaknesses when selected material permits. This is a deterministic operational policy, not measured difficulty or a calibrated recommendation.

The five-target catalog supplies only one exercise per target. Use at most one question per target; do not manufacture variants, transfer identities or repetition to meet a count. If eligible pools cannot fill a request, non-due previously practised targets can fill remaining slots as explicitly pinned reinforcement. These answers still receive feedback but cannot advance retention or create an independent failure. Assessment sessions already prepared before another answer retain their original role. Existing assistance rules continue to apply to assessments. Insufficient compatible distinct targets retains the current `insufficient_content` response; a future learner flow must offer an honest shorter request.

Read immutable revisions from the pinned foundation release in PostgreSQL, require editorial identities and filter client capabilities before allocation. Retired targets are excluded from new selection; replay continues to return existing pinned questions. Request IDs remain owned, unchanged requests replay the original allocation after history/clock changes, and altered requests conflict. Save the selection version in the session engine version; evaluation versions remain separately pinned in evidence. No client contract changes are required.

The local launcher explicitly uses unpublished draft foundation content. This does not enable publication. Profile-level filtering, topic focus, seeded variant choice, broader subject/form diversity and production release eligibility require expanded reviewed content and transport. Public target/sync reads, production authentication/database adapters and durable clients remain subsequent slices. PGlite concurrency is evidence for one local adapter only.

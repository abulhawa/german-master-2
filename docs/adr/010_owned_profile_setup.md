# ADR 010: Owned profile setup in the isolated journey

Accepted for the local demonstration, 4 October 2026.

Add authenticated, no-store `GET /v2/profile` and `POST /v2/profile` with generated v2 TypeScript/Zod and Kotlin contracts. Preferences carry English/German locale, validated IANA timezone, B1/B2 level and a five/fifteen-question session preference. Profile responses expose revision and setup completion without identity. Migration 004 extends existing fixture profiles with B1, fifteen questions, revision zero and incomplete setup. Legacy sessions, requests, evidence and schedules remain unchanged. Reads create default owned fixture profiles, consistent with the existing read adapter.

Writes hold the same learner lock as evidence ingestion. A request ID stores its exact payload and original response atomically with the revision increment. Changed replay payloads and stale expected revisions return distinct 409 conflicts. Exact replay returns the original response even after later edits; clients read the latest profile afterward. This prevents a lost response from applying an old timezone or level again. Failed replay-record insertion rolls back the entire write. Production identity, account partitions, cursor integration and independent PostgreSQL connections remain separate gates.

Level bounds **new** content. The draft release only has B1 targets; a fresh B2 preference has no eligible questions. Targets with accepted practice history remain eligible for review across level changes. The owned catalog reports this same availability rather than suggesting new B2 exercises exist. Session replay precedes availability checks, preserving both mixed and focused sessions. Session length is a preference, not permission to fabricate content; the client explicitly requests the available smaller count. Server exact-count validation remains unchanged.

Timezone changes apply at the next event ingestion under the learner lock. Stored event timezones, local dates, UTC schedules, evidence and projections are never rewritten by profile edits. Displayed review dates use the current saved timezone. This does not promise that late unsynced answers use their answer-time profile; the accepted policy explicitly saves the ingestion timezone.

The development-only web journey requires setup before new practice, offers later preference editing and preserves unfinished practice. A separate versioned fixture storage key freezes pending setup requests before HTTP and restores them on reload. Storage failures block setup writes; unreadable records are preserved. Retry sends the same request. Explicit reload reads current server preferences and abandons the pending setup request, allowing correction after conflict or invalid input. Existing practice drafts, pending answers and requests are untouched. An existing session can be resumed while setup is unresolved. Quick language/theme controls remain local preview overrides; only Save preferences updates the server profile. Saved locale is reapplied on reload.

The setup form uses shared semantic controls, labelled fields, 48px control targets, bilingual resource keys and deliberate heading focus. The 2.0 blueprint continues to supersede legacy permanent practice navigation, accuracy/streak emphasis and component-library requirements as documented in ADRs 008/009. No production deployment, reviewed-content publication, native learner journey, offline reconciliation or full accessibility acceptance is established.

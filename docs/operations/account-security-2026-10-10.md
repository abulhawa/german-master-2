# Account sign-in details — 10 October 2026

The web Account screen now displays the email returned by the verified auth user and offers Change email and Reset password. Email is kept in provider memory, never in learner stores or authorization claims. Local-only access, invalidated bindings and expired verification do not display a stale address or enable these actions.

Reset password opens the existing email request form with the verified address prefilled. No email is sent until explicit submission. Back to Account restores the Account route and saved learner work. This flow uses the established frontend recovery callback and never changes a password directly.

Change email checks the current verified subject and binding before calling Supabase `updateUser({email}, {emailRedirectTo})`. Requests use the frontend root callback, prevent duplicate submissions and expose localized pending/error/cooldown states. The UI distinguishes request acceptance from verification and keeps displaying the current verified email until the provider reports the confirmed change. Learner identity/storage remain keyed by subject, not email. Account-switch regression coverage rejects a mismatched subject before the update request.

Supabase's documented default secure email-change policy confirms through both inboxes; UI instructions also allow the provider to request only the new inbox. The existing live provider's read-only public settings endpoint returned `mailer_autoconfirm: false`. No provider setting was changed. The secure-email-change toggle itself was not exposed by that public endpoint. Actual delivered change-email acceptance is still required before calling the new flow production-accepted; no live address was changed during these checks. Reference: [Supabase updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser).

Both forms focus their page heading. Existing foundation controls, focus styling, spacing and theme tokens are retained; labels and feedback support English/German. Long email text wraps without horizontal overflow at 320 CSS pixels. Local mocked-provider browser checks exercise actual Account → Change email → pending → Back and Account → Reset password with heading focus, in English and German. Desktop/phone screenshots are retained privately under ignored `.local/account-security-preview/`. These checks do not use production accounts or send real emails.

Verification: root generated/type checks and production learner/API builds pass. The reset/email-display baseline passed the full root suite (196 backend, 421 web, 20 HTTP tests). After adding email change, the full web suite passes 423 tests; final focused provider suites pass 26 tests, including expiry and changed-subject rejection. React review: unconditional hooks, provider-owned verified email, no additional render-time requests, accessible labels/heading focus, token-based controls and responsive email wrapping. Android was not changed. This owner-requested Account improvement does not advance queued milestones or reopen accepted M1 gates. M2 remains the active milestone. No push or deployment is included.
